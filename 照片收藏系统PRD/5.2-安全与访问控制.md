# 5.2 安全与访问控制

| 模块信息 | 内容 |
|---------|------|
| **模块编号** | 5.2 |
| **模块名称** | 安全与访问控制 |
| **优先级** | P0-P2（分级实现） |
| **依赖模块** | 5.1（用户与账户管理 — 本模块的权限规则作用于 5.1 管理的用户实体） |

---

## 模块概述

本模块是系统的安全核心，统一管理所有访问控制、数据加密、身份验证增强和安全审计功能。RBAC（基于角色的访问控制）模型在本模块中唯一权威定义，消除跨模块的权限定义重复。本模块覆盖从用户登录认证到数据存储加密的全链路安全防护。

---

## 子功能详细说明

### 5.2.1 RBAC 权限体系

| 功能 | 描述 | 优先级 |
|------|------|:------:|
| 角色定义 | 预置角色：超级管理员、标准用户、协作者、访客 | P0 |
| 自定义角色 | 管理员可创建、编辑、删除自定义角色 | P1 |
| 权限矩阵 | 基于角色的细粒度权限配置 | P0 |
| 资源级权限 | 相册级、照片级的访问权限控制 | P1 |
| 权限继承 | 用户可同时拥有多个角色，权限取并集 | P1 |
| 权限组 | 将常用权限组合为权限组，便于批量分配 | P2 |

**系统角色定义：**

| 角色 | 描述 | 适用场景 |
|------|------|---------|
| **超级管理员** | 系统最高权限，管理所有配置和用户 | 系统 owner |
| **标准用户** | 可上传/管理自己的照片、创建相册、分享 | 普通家庭成员 |
| **协作者** | 可查看/上传到被邀请的共享相册 | 被邀请的协作者 |
| **访客** | 仅通过分享链接浏览内容 | 分享链接访问者 |

**权限矩阵（权威定义）：**

| 权限项 | 超级管理员 | 标准用户 | 协作者 | 访客 |
|--------|:--------:|:------:|:-----:|:---:|
| 系统配置 | ✅ | ❌ | ❌ | ❌ |
| 用户管理 | ✅ | ❌ | ❌ | ❌ |
| 存储管理 | ✅ | ❌ | ❌ | ❌ |
| 查看审计日志 | ✅ | ❌ | ❌ | ❌ |
| 管理安全策略 | ✅ | ❌ | ❌ | ❌ |
| 管理插件 | ✅ | ❌ | ❌ | ❌ |
| 上传照片 | ✅ | ✅ | ⚠️ 共享相册 | ❌ |
| 管理自己的照片 | ✅ | ✅ | ⚠️ 共享内容 | ❌ |
| 创建相册 | ✅ | ✅ | ❌ | ❌ |
| 浏览公开内容 | ✅ | ✅ | ✅ | ✅ 仅分享内容 |
| 分享照片 | ✅ | ✅ | ❌ | ❌ |
| 使用 API | ✅ | ✅ | ❌ | ❌ |
| 查看 AI 分类结果 | ✅ | ✅ | ✅ | ❌ |

**用户故事：**

> 作为超级管理员，我希望为不同用户分配不同角色，以便控制各成员的访问权限。

> 作为超级管理员，我希望创建一个"项目经理"自定义角色，拥有创建相册和邀请协作者的权限但不具备用户管理权限。

> 作为标准用户，我希望创建私有相册并设置访问权限，以便只让特定的人查看。

**验收标准：**

```gherkin
Scenario: 角色权限控制
  Given 系统中存在"标准用户"角色
  When 标准用户尝试访问系统配置页面
  Then 系统拒绝访问并显示"权限不足"提示

Scenario: 资源级权限控制
  Given 用户A创建了一个私有相册
  And 用户A未授权用户B访问该相册
  When 用户B尝试浏览该相册
  Then 系统不显示该相册
  And 用户B通过直接 URL 访问时返回 403

Scenario: 自定义角色
  Given 管理员创建了"项目经理"角色
  And 分配了"创建相册"和"邀请协作者"权限
  When 将用户B的角色设为"项目经理"
  Then 用户B可以创建相册和邀请协作者
  And 用户B无法访问系统配置和用户管理
```

### 5.2.2 数据加密

| 功能 | 描述 | 优先级 |
|------|------|:------:|
| 传输加密 | TLS/HTTPS 加密所有数据传输 | P0 |
| 静态加密 | AES-256-GCM 加密存储敏感数据（可选开启） | P1 |
| 端到端加密 | 客户端加密后上传，服务端无法解密（可选高级功能） | P3 |
| 密钥管理 | 加密密钥的安全存储与轮换策略 | P1 |
| 内网自签证书 | 支持内网环境使用自签 TLS 证书 | P0 |

**加密方案详情：**

| 加密类型 | 算法 | 用途 | 优先级 |
|---------|------|------|:------:|
| 传输加密 | TLS 1.2+ | 所有网络通信 | P0 |
| 静态加密 | AES-256-GCM | 敏感数据存储（可选开启） | P1 |
| 密码哈希 | Argon2id | 用户密码存储 | P0 |
| API 令牌签名 | HMAC-SHA256 | API 访问令牌 | P2 |
| 端到端加密 | AES-256-GCM + RSA | 客户端加密（可选） | P3 |

**用户故事：**

> 作为超级管理员，我希望启用静态加密功能，以便即使服务器被物理访问，数据也无法被直接读取。

> 作为超级管理员，我希望为内网部署配置自签 TLS 证书，以便局域网内的数据传输也是加密的。

**验收标准：**

```gherkin
Scenario: 传输加密
  Given 系统已配置 TLS 证书
  When 客户端通过 HTTP 访问
  Then 系统自动重定向到 HTTPS
  And 所有数据传输均通过 TLS 加密

Scenario: 静态加密开启
  Given 管理员启用了静态加密
  When 系统存储用户数据
  Then 敏感字段（如恢复码、2FA 密钥）使用 AES-256-GCM 加密存储
  And 密钥与数据分离存储
```

### 5.2.3 双因素认证（2FA）

| 功能 | 描述 | 优先级 |
|------|------|:------:|
| TOTP 支持 | 支持 Google Authenticator / Microsoft Authenticator 等标准 TOTP 应用 | P2 |
| 恢复码 | 启用 2FA 时生成一次性恢复码（如 10 个），用于设备丢失时恢复 | P2 |
| 强制策略 | 管理员可强制所有用户或特定角色启用 2FA | P2 |
| 信任设备 | 记住已验证的设备（可配置信任时长），减少重复验证 | P2 |
| 2FA 状态管理 | 用户可查看、启用、禁用自己的 2FA | P2 |

**用户故事：**

> 作为超级管理员，我希望启用双因素认证并强制所有用户使用，以便提升系统整体安全性。

> 作为用户，我希望在启用 2FA 后获得恢复码，以便手机丢失时仍能恢复账户访问。

**验收标准：**

```gherkin
Scenario: 启用 2FA
  Given 用户已登录
  When 用户进入安全设置并选择启用 TOTP 双因素认证
  Then 系统显示 QR 码和手动输入密钥
  And 用户使用 Authenticator 扫描 QR 码后输入验证码
  Then 2FA 启用成功
  And 系统显示一次性恢复码

Scenario: 2FA 登录验证
  Given 用户已启用 TOTP 双因素认证
  When 用户输入正确的用户名和密码
  Then 系统要求输入 TOTP 验证码
  And 验证通过后允许登录
  And 验证失败 3 次后锁定该登录尝试

Scenario: 使用恢复码
  Given 用户已启用 2FA 但丢失了认证设备
  When 用户使用一个未使用的恢复码登录
  Then 登录成功
  And 该恢复码被标记为已使用，不可重复使用
```

### 5.2.4 会话管理与访问控制

| 功能 | 描述 | 优先级 |
|------|------|:------:|
| JWT 令牌认证 | 使用 JWT 进行无状态身份验证 | P0 |
| 会话超时 | 可配置的会话超时时间（默认 30 天，可调整） | P1 |
| 并发登录控制 | 可配置最大并发会话数（默认：不限制） | P1 |
| 强制登出 | 管理员可强制指定用户下线 | P1 |
| 设备管理 | 用户可查看和管理自己的活跃会话/设备 | P1 |
| IP 白名单（可选） | 限制特定 IP 段才能访问系统 | P2 |

**用户故事：**

> 作为超级管理员，我希望查看所有在线用户并在必要时强制某个用户下线，以便应对安全事件。

> 作为用户，我希望查看自己所有活跃的登录设备，以便发现异常登录并及时处理。

**验收标准：**

```gherkin
Scenario: 会话超时
  Given 系统配置会话超时为 24 小时
  When 用户登录后超过 24 小时未活动
  Then 会话自动失效
  And 用户需要重新登录

Scenario: 强制登出
  Given 管理员强制用户B下线
  Then 用户B的所有活跃会话立即失效
  And 用户B下次操作时被重定向到登录页面
```

### 5.2.5 审计日志

| 功能 | 描述 | 优先级 |
|------|------|:------:|
| 登录日志 | 记录用户登录/登出事件（时间、IP、设备信息） | P1 |
| 操作日志 | 记录关键操作（上传、删除、分享、权限变更、系统配置修改） | P1 |
| 日志查看 | 管理员查看审计日志（支持按用户、时间、操作类型筛选） | P1 |
| 日志导出 | 导出审计日志为 CSV/JSON 格式 | P2 |
| 日志保留策略 | 可配置日志保留期限（默认 90 天） | P2 |
| 日志防篡改 | 审计日志只追加不可修改（append-only） | P1 |

**记录的操作类型：**

| 类别 | 操作 |
|------|------|
| 认证 | 登录、登出、登录失败、密码修改、2FA 启用/禁用 |
| 数据 | 照片上传、照片删除、照片编辑、元数据修改 |
| 组织 | 相册创建/删除、标签创建/删除、照片移动 |
| 分享 | 分享链接创建/撤销、协作邀请、分享访问 |
| 权限 | 角色变更、权限修改、用户禁用/启用 |
| 系统 | 系统配置修改、备份执行、插件安装/卸载 |

**用户故事：**

> 作为超级管理员，我希望查看审计日志了解系统中的关键操作，以便进行安全审计。

> 作为超级管理员，我希望导出某段时间内的审计日志，以便进行离线分析或合规审查。

**验收标准：**

```gherkin
Scenario: 审计日志记录
  Given 用户A删除了一张照片
  When 管理员查看审计日志
  Then 日志中记录了删除操作
  And 包含操作者（用户A）、操作时间、操作类型（DELETE_PHOTO）、操作对象（照片ID）
  And 包含 IP 地址和 User-Agent

Scenario: 审计日志筛选
  Given 系统中存在大量审计日志
  When 管理员按"用户B"+"最近7天"+"删除操作"筛选
  Then 仅显示符合条件的日志记录

Scenario: 日志防篡改
  Given 审计日志已记录
  When 任何人（包括管理员）尝试修改或删除日志条目
  Then 操作被拒绝
```

### 5.2.6 隐私策略与数据保护

| 功能 | 描述 | 优先级 |
|------|------|:------:|
| 个人资料可见性 | 控制其他用户是否可查看个人资料（头像、昵称、简介） | P1 |
| 在线状态隐私 | 控制是否向其他用户显示在线状态 | P2 |
| 活动隐藏 | 控制是否在"最近活动"中隐藏自己的操作 | P2 |
| 数据导出 | 用户可导出自己的所有数据（照片 + 元数据） | P2 |
| 账户注销 | 用户可申请注销账户，系统在确认后删除所有个人数据 | P2 |
| 防暴力破解 | 登录失败 N 次后锁定账户（N 可配置，默认 5 次） | P0 |
| CSRF 防护 | 所有表单提交携带 CSRF Token | P0 |
| 安全响应头 | 设置 Content-Security-Policy、X-Frame-Options 等安全头 | P0 |

**用户故事：**

> 作为用户，我希望导出自己的所有照片和元数据，以便迁移到其他平台。

> 作为用户，我希望注销账户并彻底删除所有个人数据，以便保障隐私权。

**验收标准：**

```gherkin
Scenario: 防暴力破解
  Given 系统配置登录失败锁定阈值为 5 次
  When 同一账户连续 5 次输入错误密码
  Then 该账户被自动锁定 15 分钟
  And 管理员在审计日志中看到锁定事件

Scenario: 数据导出
  Given 用户请求导出自己的数据
  When 系统准备完成
  Then 用户可下载包含所有照片原始文件和元数据的压缩包
```

## 模块级用户故事

> 作为超级管理员，我希望通过一个统一的安全管理界面配置所有安全策略（RBAC、加密、2FA、审计），以便全面掌控系统安全。

> 作为安全合规负责人，我希望系统具备完整的审计日志和防篡改机制，以便满足数据保护合规要求。

> 作为用户，我希望系统默认使用 HTTPS 加密传输，以便我的数据在局域网中也不会被窃听。

## 模块级验收标准

```gherkin
Scenario: 端到端安全链路
  Given 系统已配置 TLS + 启用静态加密 + 启用审计日志
  When 用户通过 HTTPS 登录并上传照片
  Then 传输过程使用 TLS 加密
  And 存储的敏感数据使用 AES-256 加密
  And 登录和上传操作均记录在审计日志中

Scenario: 权限隔离验证
  Given 系统中存在超级管理员、标准用户、协作者三种角色
  When 分别以三种角色登录
  Then 每种角色只能执行其权限矩阵中允许的操作
  And 无法越权执行其他角色的操作
```

## 依赖关系

```
5.2 安全与访问控制
  ├── 依赖：5.1 用户与账户管理（权限规则作用于用户实体）
  ├── 被依赖：5.3 媒体导入与存储（上传操作需权限验证）
  ├── 被依赖：5.5 组织与分类（相册/标签操作需权限验证）
  ├── 被依赖：5.8 媒体编辑（编辑操作需权限验证）
  ├── 被依赖：5.9 媒体管理与生命周期（删除/归档操作需权限验证）
  ├── 被依赖：5.10 分享与协作（分享操作需权限验证）
  ├── 被依赖：5.12 开放平台与运维（API 访问需令牌认证）
  └── 被依赖：所有模块（全局安全拦截）
```

> **说明**：RBAC 权限矩阵在本模块中唯一权威定义。其他模块引用权限时均以本模块为准，不重复定义。
